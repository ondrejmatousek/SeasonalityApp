# H4 paper research v1 — separate prospective experiment

The original `fm-h4-touch-2r-v1` engine, SQL tables, frozen setups, OCO, costs and outcomes are unchanged. Research never calls its updater or writes its tables. Static hosting performs the original update first, then an independent, best-effort research step. Research failures publish an unavailable marker, not invented/reset statistics, and do not block the baseline dashboard.

## Frozen experiment

`fm-h4-research-v1` starts when its separate SQL state is first created. Existing original trades remain visible as retrospective descriptive cohorts; they do not count towards the prospective 100. The new SQL schema `paper_research` is created by the explicit deployment CLI, not by web requests. State has CAS revisions, hashes, immutable frozen scenarios, terminal results, append-only event prefixes and immutable checkpoint prefixes. An implementation hash pins the research code and the original helper engine. Code/rule changes require a versioned experiment, never reinterpretation of prior outcomes.

Six predeclared comparisons:

1. Original direct-touch 2R.
2. Original trades whose frozen BOS state was `yes`.
3. Original trades whose frozen volume state was `high` (same existing 1.5x median rule).
4. Independent direct-touch 3R, original 5% zone-height stop buffer.
5. Independent direct-touch 2R, 10% zone-height stop buffer.
6. Independent verified M15 SFP, next-open entry, 2R, original 5% zone stop.

Groups 2/3 are overlapping observational cohorts, NOT separate full filtered-strategy portfolios. In particular they do not recreate opportunity selection or OCO under a hypothetical filter. Their R cannot be added. Independent simulations 4–6 have their own OCO, lifetime and admission; positions lasting longer may correctly prevent later registrations. Baseline zone identity is retained. Only newly registered baseline scenarios still waiting when first observed can enter a sidecar. No retrospective replay/fills of historical baseline trades.

M15 is **implemented but inactive until verified live data exists**: `price.m15`, same exact OANDA symbol, ready, M15 timeframe, completed source `asOfUtc`, `rawSha256`, validation rule `oanda-m15-boundary-v1`, `providerBoundaryValidated:true`, `completedOnly:true`. No H4 interpolation or offline lab pilot substitution. No M15 collector/job is enabled here. Working SFP rule: after first future zone touch, within eight M15 intervals, sweep the latest confirmed strict 2-left/2-right pivot and close back over it (inverse short). Pivot must be known before the signal bar. Entry is next M15 open, not signal close. A prior close beyond the zone distal edge cancels; next open beyond stop cancels. Frozen rule, pivot evidence, signal bar and entry/exit bars are audited. Price model still lacks actual bid/ask and broker-specific execution rules.

All branches retain missing/revised-price guards and ambiguous same-bar outcomes; no guessed outcomes, no retrospective registration, no double fills. Costs are the original working assumptions, financing unmodeled. No live broker orders or automatic promotion.

## Statistics and checkpoints

Only fully evidenced TP/SL with finite gross/cost/net R count. Waiting/open/cancelled/ambiguous/needs-data are disclosed separately. Metrics: total and mean net R, PF (undefined without losses), closed-trade-only drawdown, double-cost stress, UTC entry-day count. Deterministic day-block bootstrap (1000 samples, 95% interval) is withheld with fewer than five entry days; Wilson win-rate bounds are included in JSON. These are descriptive approximations, not guaranteed independence, a multiple-testing correction, mark-to-market equity or account returns.

First publication with at least 100 prospectively registered, closed baseline trades creates an immutable discovery report with actual sample sizes, hashes and baseline revision. This is not necessarily exactly 100: one new candle/publication can close several trades. Candidate selection is predeclared: at least 30 closures, 10 UTC entry days, positive bootstrap lower bound and positive double-cost mean; highest mean among eligible, stable-ID ties. No candidate is a valid outcome. Pending positions and differing variant sample sizes remain visible; discovery does not prove a trading edge.

Validation starts from **registration after the saved discovery report**. Trades registered earlier but closing later cannot enter it. Once 100 newly registered baseline trades close, save a second immutable report for the already selected candidate; do not select a new winner using validation results. Passing the same working positive-result gates does not establish live profitability. Human review and more data can still be required.

Reports are generated by publication even with no browser open. The dashboard expands and displays an alert when a saved checkpoint appears; JSON includes reports and independent simulation audits. This is an in-app notification, NOT an email, push message or new scheduled agent task. Browser reads only. Failures retain the last displayed state with an explicit stale/unavailable warning.

## Checks

- `node Tools/h4-paper-research-checks.cjs`: prospective isolation, checkpoint/holdout boundaries, immutability, clustered uncertainty, independent geometry/OCO, gaps/revisions, verified-only M15 SFP.
- `dotnet build Tools/PaperResearchStore/PaperResearchStore.csproj -c Release` and `node Tools/h4-paper-research-store-checks.cjs`: validate-only, no SQL, frozen policies/results/audits and public-report consistency.
- `node Tools/h4-paper-research-browser-checks.cjs <rendered-site>`: real browser, 1440/390/320 layout, sample separation, checkpoint alert/download, research outage cannot erase baseline.
- Existing H4 paper engine/store tests still apply unchanged. Production verification compares the original ledger's frozen and terminal-record prefixes, not just total counts or a green deployment.
